## 1. Purpose

This document translates the frozen Kaifa v2 Product, Engineering, Runtime, Engine, Event, UI/UX, Frontend, Feature, and Backend task documentation into executable MVP integration and QA tasks. It is the QA source of truth for frontend-backend integration, API contract verification, database and migration verification, Runtime and official event verification, Assessment Engine integration, Placement Test E2E, AI Conversation Practice integration, authentication and learner isolation, observability and audit verification, regression testing, and MVP release readiness.

## 2. Scope and Guardrails

* Executable MVP QA tasks use `QA-TASK-###` only.
* Future Phase 2 work uses `QA-FUTURE-P2-###`; future Phase 3 work uses `QA-FUTURE-P3-###`; unresolved/open work uses `QA-BLOCKED-###`.
* No MVP QA task depends on future or blocked work.
* QA verifies frozen contracts and must not introduce architecture, entities, columns, APIs, official events, engines, business rules, screens, components, or MVP capabilities.
* Runtime owns orchestration, state transitions, and Activity Result persistence.
* Learning Activity remains official publisher of `LearningActivityCompleted` and `ActivityResultGenerated`.
* Activity Result remains Runtime-owned and non-evaluative.
* Assessment Engine remains sole producer/writer of immutable Assessment Result.
* MVP Runtime stops at `AssessmentResultGenerated`; Knowledge Profile and Learning Decision remain Phase 2.
* AI Layer and frontend do not create official learning outputs or Official Runtime Events.
* `AssessmentFailed` remains observability-only, not an Official Runtime Event, not a business trigger, and creates no Assessment Result.
* Placement Test remains a specialized assessable Learning Activity with no placement-specific table, engine, API family, result owner, or official event.
* MVP AI Conversation Practice covers text, learner voice, mandatory STT/TTS, canonical transcript, replay/retry, fallback, Normal and Assessable Practice, approved evidence, provider observability, safety, and graceful degradation.

## 3. Integration and QA Principles

* Test from frozen contracts first: API, DB, event, engine, UI state, and task breakdowns are authoritative.
* Prefer automated evidence for contract, migration, event, E2E, accessibility, and regression checks.
* Verify ownership boundaries explicitly; a passing happy path is insufficient when architecture authority is at risk.
* Separate official Runtime Events from audit, logs, traces, provider records, safety records, and observability-only failure records.
* Exercise both success and failure branches for completion, assessment, auth, provider, STT, TTS, idempotency, retry, replay, and rollback.
* Use two-Learner fixtures for every learner-owned read/write surface.
* Treat frontend loading, empty, error, retry, unauthorized, expired session, focus, accessibility, and responsive behavior as integration requirements, not polish.
